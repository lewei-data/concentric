## 0. 一句话结论

**OpenMontage 里没有 "配音阶段"**——`tts_selector` 是 `assets` 阶段的*必需*工具。

所以四个岗位不能按阶段切，只能按**字段和文件**切。

**推入时机**：立项/调研/proposal 在选题确定时即可由 CCO 自主完成（2026-11-13 授权）；**开工生成素材**仍以文案与分镜成稿为界（`script` 阶段入口）。

判定条件见第 4 节。

## 2. 字段级交接契约（真正的 "匹配" 发生在这里）

### 2.1 `proposal_packet.json`（cco 定并自批；cco 自建项、自跑 checkpoint）

必须含：



* `concept_options` ≥ 3 个，结构 /hook/ 受众要真的不同

* `selected_concept`

* `cost_estimate.line_items`（逐项、按实际可用工具报价）

* `render_runtime`：`remotion` | `hyperframes`

* `approval.status` = `approved` 或 `approved_with_changes` 才能往下走；CCO 自批同样落这两个值，并在 `decision_log.json` 记 `self_approve` + 依据

**为什么&#x20;**`render_runtime`**&#x20;必须在这里定死**：`compose` 阶段的 review\_focus 原文写着 ——

`edit_decisions` 里的 `render_runtime` 与 `proposal_packet` 不一致 = **CRITICAL governance**

**violation（静默切换运行时）**，vd 无权中途改。这条对应的业务语言就是你 `pipeline.yaml`

里 assessment 阶段那句 "CCO 确定出片模式（科普类 remotion 合成 / 娱乐类全视频或语音 + 视频）"。

### 2.2 `script.json`（PM 写）

结构照 `projects/cxl-memory-pooling/artifacts/script.json`，schema 在 `schemas/artifacts/`。

必填：



* `total_duration_seconds`

* `voice_performance`：`performance_intent` / `pacing_profile` / `energy_curve` / `pause_policy` /

  `sample_section_id` / `provider_notes`

* `sections[]`：`id` / `label` / `text` / `start_seconds` / `end_seconds` /

  `speaker_directions` / `delivery_cues`（`pace`、`energy`、`emphasis_words`、

  `pause_before_seconds`、`pause_after_seconds`、`delivery_note`、`provider_text`）/

  `enhancement_cues[]`（`type`、`description`、`timestamp_seconds`）

`provider_text`**&#x20;规则（最容易踩）**：Piper 不解析 SSML，`<break/>` 会被当字符读出来。

所以 `provider_text` 必须是干净的朗读文本，不含任何标签；节奏靠标点和换行控制。

这段责任在 **PM**，不在配音岗 —— 配音岗拿到 `provider_text` 直接喂，不二次改文字。

校验线（def 的 success\_criteria）：



* 字数在目标时长 ±10% 以内

* `enhancement_cue` 密度约 1 个 / 8–10 秒

* 有 speaker directions、有 voice performance plan

* 叙事弧：hook → setup → build → climax → landing

PM 交付标准（2026-11-13 老板要求）：文案要"丰富到位"，不是概念复述——每段有情绪、重音、停顿与节拍标注，`provider_text` 可直接喂 TTS；写完落 `projects/<slug>/artifacts/script.json` 并过 schema 校验、写 `pipeline/<slug>/checkpoint_script.json`。**邮件/聊天/口头不算交付，配音岗只从该文件接单。**

### 2.3 `scene_plan.json`（PM 写）

必填：



* `style_playbook`（如 `tech-dark-diagram`）

* `scenes[]`：`id` / `type` / `description`（**五段式**：Subject / Subject Motion / Scene /

  Spatial Framing / Camera）/ `start_seconds` / `end_seconds` / `script_section_id` /

  `framing` / `movement` / `transition_in` / `transition_out` / `overlay_notes` /

  `narrative_role` / `shot_intent` / `information_role` / `hero_moment` /

  `texture_keywords` / `required_assets[]`（`type`、`description`、`source`）

校验线：



* 覆盖全片时长、无空隙无重叠

* 连续同类型镜头不超过 2 个（不能 3 连）

* 每镜 `required_assets` 必须是生产计划里真有的工具

* 至少 3 种不同镜头类型

`required_assets` 的 `type` / `source` 就是 vd 的执行指令，`description` 是五段式才可执行。

PM 交付标准（2026-11-13 老板要求）：运镜（`framing` + `movement` + `shot_language`）、节拍（起止秒 + `script_section_id` 对齐）、转换（`transition_in` / `transition_out` + `overlay_notes`）必须**逐镜**写到可执行，缺一项即视为未完成，不得以"展示相关内容"之类空话交差；写完落 `projects/<slug>/artifacts/scene_plan.json` 并过 schema 校验、写 `pipeline/<slug>/checkpoint_scene_plan.json`。**vd 只从该文件接单，不接受聊天转述。**

### 2.4 `audio_manifest.json`（配音岗写・本文件新增的约定）



```
{
  "version": "1.0",
  "voice": { "provider": "piper", "model": "zh_CN-chaowen-medium", "length_scale": 1.15 },
  "items": [
    { "section_id": "s1", "file": "assets/audio/s1.wav",
      "duration_seconds": 6.83, "lufs_mean": -20.3, "peak_dbfs": -3.1 }
  ]
}
```

为什么需要它：`assets` 门要求 " 旁白覆盖全部 sections 且符合已批准的 voice performance

plan"，而 `av_sync_check` 要按**真实时长**对齐。没有这张表，vd 只能拿 wav 逐个 ffprobe

反推，极易错半拍并返工。

### 2.5 `asset_manifest.json`（vd 写・单写口）



* 所有 `file path` 必须真实存在（def 的 success\_criteria 原话：`All file paths resolve to existing files`）

* 覆盖 `scene_plan` 每镜的 `required_assets`

* 音频（引用 `audio_manifest`）与画面都在同一张表里

## 3. `assets` 是唯一必须拆两拍的阶段

因为音频和画面同属 `assets`，但 `asset_manifest` 只能有一个写口。



| 拍次  | 谁   | 做什么                                                                                | 产出                                                          |
| --- | --- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 拍 1 | 配音岗 | 读 `script.json` 的 `provider_text` + `delivery_cues` → 出分轨 wav；按 `music_library` 选曲 | `assets/audio/*.wav`、`assets/music/*`、`audio_manifest.json` |
| 拍 2 | vd  | 以 `audio_manifest` 的**实测时长**为时间轴基准 → 排镜长 → 生成 / 取画面 → 音画对齐                         | \`assets/images                                             |
| 门   | PM  | 确认素材                                                                               | 过门才进 edit /compose                                          |

顺序不能反：先有音频实测时长，才有正确的镜长与 `av_sync`。

### 3.1 素材质量红线（2026-11-13 老板要求）

两个岗位都从管线主动取活、补齐缺口，但**不许为凑齐清单降级**：

* **配音**：先用 `sample_section_id` 试音，断句、重音、停顿、数字/英文/专名读法不过关就换音色或调 `length_scale`，不拿"能出声"交差；逐段 ffprobe 实测时长、响度、峰值写进 `audio_manifest`，不削波、不爆音，段时长偏差 >15% 回 PM；BGM 只能来自 `music_library` 或生成，取不到就写 `music_status: unavailable` 上报，禁止静默无 BGM。
* **画面**：按需求选通道，不是一律丢给扩散模型——精确文字走 Remotion `text_card` / SVG（baoyu-infographic、architecture-diagram），示意图走 Mermaid `diagram_gen`，写实图走 `generate-image`（≥25 步、832×640、带负向词），微动走 `animatediff`，真实运动才用 `wan21` 480P 短镜，数学动画走 `manim-video`，程序化视觉走 `p5js`。
* **质检不过不投料**：同一镜最多生成 2 次，仍不达标就换路线或报 PM 改分镜；糊图、错字图、手指/五官畸形图一律判废。质检结论与 prompt/seed/steps/重试次数写进 `asset_manifest.json`。
* **写口唯一**：配音只写 `audio_manifest.json` + `assets/audio|music/`；`checkpoint_assets.json` 由 vd 汇总两份清单后统一落盘（PM 过门时 `human_approved=True`），避免双写冲突。

## 4. 推入时机（本文核心）

### 4.1 推荐推入点

**PM 交付&#x20;**`script.json`**&#x20;+&#x20;**`scene_plan.json`**&#x20;之后、vd 开始生成任何素材之前。**

即 OPC 流水线里 `copy` 定稿 → `sample` 开工那一步；对应 OpenMontage 的 `script` 阶段入口。

**三个前置件，缺一不推**：



| # | 前置件                   | 怎么判                                                                                                                    |
| - | --------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 1 | `render_runtime` 已定   | 有 `proposal_packet`（哪怕最小版，只含 `selected_concept` + `render_runtime` + `cost_estimate`）；或 PM 派单里写明 remotion /hyperframes |
| 2 | `script.json` 字段齐     | 有 `voice_performance`；每段有 `speaker_directions` 和 `delivery_cues`；`provider_text` 无标签                                   |
| 3 | `scene_plan.json` 对得上 | 每镜有 `required_assets`；`script_section_id` 的集合与 `script.json` 的 `sections[].id` 一致                                      |

### 4.2 立项可以早，素材开工不能早（2026-11-13 修订）



* `research` 阶段 `checkpoint_required: false`、`human_approval_default: false`、

  `tools_available: []`——本身不调渲染工具；但 proposal 的前置校验要求 research 检查点为 `completed`，所以 CCO 立项时会补写一条（无人工门）。

  调研可直接引用 scout 的产出，不需要渲染能力。

* `proposal` 的产物（3 个概念 + 逐项成本）现在由 CCO 在 montage 内自批（2026-11-13 老板授权），`render_runtime` 以 `projects/<slug>/artifacts/proposal_packet.json` 为唯一基准；OPC 侧 `production_approval` 只保留开工与预算的老板抽查，不再重复产出 runtime。

* cco / PM / 配音 / vd 四岗均已开通 terminal（工作目录限 `/opt/sefs/OpenMontage`），具备投料所需的写权限；CCO 现在可在选题确定时直接 `init_project` 建骨架、写 research/proposal 并自批，**素材开工仍按 4.1 判定**。PM/vd 接手时补齐 `script.json`、`scene_plan.json` 与素材清单。

### 4.3 为什么不是更晚（等到 assets 才推）



* `script` 与 `scene_plan` 各有硬校验线（字数 ±10%、cue 密度、≥3 种镜头类型、

  `required_assets` 必须是生产计划里的工具）。跳过校验直接生成素材，**返工范围 = 全部素材**，

  而且 `av_sync` 会建立在错误的分镜时长上。

* `assets` 的 PM 确认门会退化成 "评审一批本来就该打回的东西"，浪费 CCO/PM 的评审次数

  （`max_send_backs: 3` 是有限资源）。

### 4.4 推入后 vd 的第一步不是渲染



1. 建骨架：`projects/<slug>/` + `pipeline/<slug>/`（CCO 立项时已建，vd 接手先核对，缺则补建）

2. 把 PM 的两份 JSON 落到 `projects/<slug>/artifacts/`

3. 跑 `script` / `scene_plan` 校验（schema + 时长 + 镜头类型 + `required_assets` 可执行性），

   checkpoint 落盘

4. 校验不过 → **打回 PM**（`max_send_backs: 3`）；vd **不得改写正文**

5. 两份都过 → 才进 `assets` 拍 1，把音频任务交给配音岗

### 4.5 什么任务不该进管线



| 任务形态            | 更合适的做法                                                   |
| --------------- | -------------------------------------------------------- |
| ~~单张图 + 一句话口播~~ | `comfyui_image`~~ + TTS + ffmpeg 拼接，分钟级~~                |
| 纯剪辑 / 拼接已有素材    | `byted-mediakit-editing` 或 ffmpeg                        |
| 无旁白卡点片          | 短 def（如 `clip-factory`），不需要 `script` 的语音字段               |
| 单个试镜镜头 / 概念图    | `comfyui_image` / `comfyui_video`（见 vd 技能「ComfyUI 远程服务」） |

## 5. 门禁与返工路径



| 阶段          | 谁签                | 不过怎么办                  |
| ----------- | ----------------- | ---------------------- |
| proposal    | CCO 自批（`decision_log` + checkpoint metadata 留痕），老板可事后抽查 | 回 cco 改概念或改 runtime    |
| script      | PM                | 回 PM 改文案 / 节奏，vd 不动文字  |
| scene\_plan | PM                | 回 PM 改分镜               |
| assets（画）   | PM                | 回 vd 补 / 换素材；音频问题回配音岗  |
| edit（样片）    | CCO / CTO / PM 三方 | 回 vd 重剪，最多 2 轮         |
| compose     | 审核员               | 回 vd 修，或退回 PM 改文案      |
| publish     | 老板（发布审批）          | release\_ops 执行，vd 不发布 |

## 6. 当前缺口（按修复成本排序）



1. `music_library/`**&#x20;是空的**（5 分钟应急）：pixabay 从本机 403，157 上没有音乐模型，

   `music_gen` 这个可选工具落不了地。"配音岗提供音乐" 目前**没有物理来源**。

   最快路径：手放 3–5 首 CC0 曲进 `/opt/sefs/OpenMontage/music_library/`，按 README 登记授权。

2. `audio_manifest.json`**&#x20;契约未正式化**（本文 2.4 即为草案）：定下 5 个字段即可，缺它必返工。

3. **voice sample 门没启用**（零成本）：`script.json` 里已有 `sample_section_id` 字段，

   OpenMontage 原本就设计了 "先出一段试音再全量"。先出这一段给 PM/CCO 试听，

   可避免全量配音做完才发现音色不对（本机中文目前只有 huayan 女声，目标若是沉稳男声

   需另配 onnx 模型）。
